Memory rules:
- **"Memory" in this repo means this file** — when the user says "update memory" or "save to memory", update this file (`CLAUDE.md`).
- Do not write repo knowledge or decisions to the user's `~/.claude/` directory or to `.agent-local/`. Those locations are machine-local and invisible to other contributors.
- All repo-level memory (design decisions, conventions, seed rules, naming choices) belongs in this file so it travels with the repo.
- The only exception is genuinely machine-specific state: absolute paths, local tool locations (e.g. `JQ_BIN`), or per-machine overrides. Those belong in `.agent-local/copilot-memory.md` or `env/common.env`, not in `~/.claude/`.
- **Update proactively, don't wait to be asked.** When a session surfaces a durable repo convention, a non-obvious fix, or a machine-setup gotcha, propose adding it to the right file (this one, or `.agent-local/copilot-memory.md`) before considering the task done — the same way you'd flag it if asked directly. Route by scope, not by where the fact was discovered: "would this help a different contributor / a different machine?" — yes → this file; no, only reproducible on this exact box → `.agent-local/`.
- **Keep this file itself lean — it's read in full every session.** A separate `.github/agent-<topic>.md` reference file, by contrast, is only opened when a task actually needs it. When adding lengthy detail that's only relevant while a specific feature is being touched (a deep troubleshooting playbook, a feature's full config reference), put the detail in its own `agent-<topic>.md` file and leave one short pointer bullet here — see `agent-linux-node-setup.md` and `agent-keycloak-saml-oidc.md` for the pattern. Detail that's relevant to *most* sessions regardless of task (naming conventions, the core `make` workflow, things every edit risks breaking) stays inline — don't over-extract to the point this file stops being a useful map of the repo.

Respect these repo-specific rules:
- Do not start stacks, run `make start`, or launch other long-running services unless the user explicitly asks.
- It is fine to make file edits proactively when the requested change is clear.
- Preserve the dataset dimension in the scaffold even when only the `sample` dataset exists.
- Treat env files in `env/` as shell-sourced files. Quote values that contain spaces.
- On Windows Git Bash, keep Docker compose path handling compatible with native Docker on Windows.
- When capturing multi-line output from an external CLI into bash (`mapfile`, `read`, command substitution), don't assume clean LF — on Windows, an npm-installed tool invoked through a `.cmd` shim (e.g. `npx ...`) can intermittently leak a trailing `\r` into a captured value (`mapfile -t`/`read` only strip `\n`). This bit us once: `mb uuid --count N --json | jq -r '.[]'` fed a `\r`-tainted UUID into a card's `lib/uuid`, which the server rejected with a vague "N error(s)" MBQL validation failure — not reproducible by re-running the same command in isolation, only caught by dumping the actual failing payload. Fix pattern: pipe through `tr -d '\r'` wherever such output is captured, rather than trusting the source tool. Worth the same suspicion for any other cross-platform script logic (path separators, case sensitivity, `\r\n` in generated files) — Windows-only intermittent failures are usually a line-ending or shim-indirection artifact, not a version/logic bug.

Tracked repo notes:
- Version env files (`env/mb_versions/*.env`) are gitignored and personal — each developer creates their own from `env/mb_versions/template.env.example`. There is no shared canonical version list. Floating `.x` filenames (e.g. `1.61.1.x.env`) track the latest patch; a full 4-part filename (e.g. `1.61.1.3.env`) pins to a specific build.
- The current dataset profile is `sample-pg15`, using `metabase/qa-databases:postgres-sample-15` from `env/dwh_source/sample-pg15.env`. The sample data warehouse service is named `sample-dwh` in Docker Compose (not `sample-db`). The Metabase connection display name is `sample_dwh_pg15`.
- **`MB_AUTOMATION_API_KEY` is generated per-stack, not shared.** `new-stack.sh` runs `mb_$(openssl rand -base64 32)` and writes the result into the new `env/mb_versions/<version>.env` file. `load_stack_env` sources `common.env` then the version env file then the dataset env file (in that order, via `set -a`), so the per-stack value naturally overrides whatever's in `env/common.env` — no special-casing needed in the loader. `env/common.env.example`'s copy of this var is just a fallback placeholder for stacks whose version env file predates this change or was created by hand without one. If you touch `new-stack.sh`'s env-file-writing heredoc, keep this line in it.
- **This repo is public.** A full secrets audit (2026-07-21) found no real user secrets in tracked files or git history — `env/common.env`, `env/mb_versions/*.env`, `.mcp.json`, and `.agent-local/` are all gitignored and confirmed never committed. `env/common.env.example` previously shipped a fixed, real `MB_AUTOMATION_API_KEY` value; as of 2026-07-21, `make new` instead generates a unique key per stack into the gitignored version env file (see the automation-key bullet below), and the example file's value was replaced with a `replace-with-random-key` placeholder matching the file's other secrets. Before adding any new tracked file under `env/`, `seed/`, or `compose/`, check it doesn't hardcode a real per-user credential — use the `replace-with-your-...` placeholder convention instead.
- **No-stacks guard for `make start`**: if the user runs `make start` (or `make stop`/`make nuke`) and gets the error `No version env files found in env/mb_versions/`, do **not** just repeat the error message. Instead, ask the user if they'd like to create their first stack, then guide them through `make new` (which walks them through choosing a Metabase version and sets up the env file). Phrase it as: "It looks like you don't have any stacks configured yet. Would you like me to walk you through `make new` to create one?"
- The public workflow is `make list`, `make start`, `make stop`, `make nuke`, `make new`, and `make done`. When `MB_VERSION` is omitted from start/stop/nuke, each invokes `scripts/pick.sh <action>` — reads `env/mb_versions/` and `env/dwh_source/`, detects running stacks via `docker compose ls`, presents an interactive numbered menu. When `MB_VERSION` is supplied, bypasses the picker and calls the script directly.
- `make done` (`scripts/done.sh`): stops all running `mb_*` stacks (via `docker compose ls`, filters out `mb_shared`) plus shared services in one command. Uses `docker compose -p <project> stop` so volumes are preserved. Intended as an end-of-day shutdown shortcut.
- `make list` (`scripts/list-stacks.sh`): shows all configured stacks (from `env/mb_versions/*.env`) with their Metabase port and running status. Running stacks show the dataset and `→ http://localhost:<port>`.
- **`STACK_LABEL`**: an optional, purely cosmetic friendly name a user can give a stack (e.g. `testing keycloak`) — it is NOT a replacement for the version/dataset identity, filename, or any env values, just a display label shown by `make list` and the `make start`/`stop`/`nuke` picker (`scripts/pick.sh`). Prompted for (optional, blank skips it) at the end of `make new` (`scripts/new-stack.sh`), written as `STACK_LABEL="<value>"` (double-quoted) in the version env file so values with spaces survive `source`. `list-stacks.sh` shows it in a `LABEL` column; `pick.sh` appends it in quotes after the `version [dataset]` menu entry. Users can also hand-edit `STACK_LABEL="<value>"` into an existing env file at any time — no script needs to run.
- `make nuke` (`scripts/nuke.sh`): removes containers, the compose network, external volumes, seed markers under `.state/`, the Firefox container entry, the metabot-debug-logs subfolder, the Claude MCP server registration, and the `mb` CLI's stored auth profile for that stack. Then prompts to also delete the version env file (answer no to keep the env file and re-start later).
- `make new` (`scripts/new-stack.sh`): drill-down flow — prompts for major version (e.g. `1.61`), fetches all stable builds for that major from Docker Hub (one request, `page_size=50`, filters to bare X.Y.Z release tags and X.Y.Z.W hotfix-build tags, excludes beta/rc/alpha), presents unique minor versions first, then hotfix builds for the chosen minor plus a float-on-`.x` option, then dataset selection. A tag's "minor" is itself for a bare 3-part release (`v1.58.22` → minor `1.58.22`, since not every release gets a hotfix) or the tag minus its trailing digit for a 4-part hotfix build (`v1.58.20.1` → minor `1.58.20`) — see `tag_minor()` in the script. The minor menu annotates `(a stack exists)` if any build/dataset variant within that minor is configured (deliberately vague — it doesn't imply the bare minor itself is pinned); the build menu one level down annotates the specific build with `(stack exists)` via an exact tag match, showing which variant it actually is. Selecting an already-configured combination exits cleanly. Version `0.x` uses repo `metabase/metabase` (OSS); `1.x` uses `metabase/metabase-enterprise`. Scans existing env files to suggest non-conflicting ports (max+10 for Metabase, max+10 for DB ports). Port conflicts are not auto-resolved — user edits the env file and retries.
- `make prune`: first removes repo-managed Metabase images whose retention window has expired, then runs `docker image prune -f` for dangling layers and `docker volume prune -f` for orphaned volumes. `scripts/nuke.sh` marks a Metabase image for cleanup once no containers still reference it; `scripts/start.sh` clears that marker when the stack is started again. Markers live under `.state/image-gc/` and default to a 30-day retention window (`IMAGE_GC_RETENTION_DAYS`, if exported in the shell).
- `scripts/common.sh` is the shared runtime layer for env loading, path normalization, stack naming, compose invocation, Metabase image refresh (pull if newer, prune old), and Metabase health waiting. Key helpers: `load_common_env` (loads `env/common.env`, pre-declares `DATASET`/`MB_VERSION` to satisfy `set -u`, configures optional tools — call this instead of repeating the inline pattern); `project_name_for <version> <dataset>` (derives the Compose project name — lives in common.sh, do not redefine it locally); `sanitize_key` (converts `.` and `-` to `_` for use in Compose project names and volume names).
- `scripts/pick.sh` calls `load_common_env` to load common settings before a stack is chosen. Running stacks detected via `docker compose ls | awk` — no jq needed for this step.
- **Firefox Multi-Account Container integration**: creation, exit codes, and the `--remove` flag live in `.github/agent-firefox-containers.md`; read that only when working on `scripts/firefox-container.sh` itself.
- Bootstrap uses `seed/metabase/config-pg15.yml` (Postgres) or `seed/metabase/config-mysql8.yml` (MySQL) — selected via `METABASE_CONFIG_FILE` in the dataset env file — plus `scripts/seed-metabase.sh` to create admin, analyst, and sales users, two groups, a starter collection, and a connectivity-check card.
- `scripts/seed-metabase.sh` drives collection/card/dashboard/database work through the `mb` CLI (the `mb_cli` helper in `common.sh`) rather than raw API payloads; user creation, permission groups/membership, and cache policy stay on direct `curl` calls since the CLI has no verb for them (see the `mb` CLI gotchas bullet below). Seed new Metabase cards with the simplest viable approach — reuse this same split rather than adding a separate metadata or template layer unless there is a strong reason.
- For GUI-query seeds that depend on Metabase field IDs, derive table and field IDs from live database metadata inside `scripts/seed-metabase.sh` instead of hardcoding raw IDs from one local stack.
- When deciding whether seeded cards or dashboards already exist, use `/api/collection/<id>/items` for the seeded collection rather than Metabase search results; search can return stale entries for content that no longer exists in the real collection state.
- The Metabase content seed uses the version marker in `.state/*.metabase-seeded` to decide when to reconcile new baseline content into an existing stack. The sample DWH seed uses `.state/*.sample-dwh-seeded`.
- When adding seeded Metabase cards, ask whether the card should also be attached to a dashboard; default to collection-only unless the user explicitly wants dashboard changes.
- If the user wants dashboard changes based on a locally edited dashboard, prefer extracting or importing the dashboard as a seeded artifact rather than hand-rebuilding dashboard layout in shell.
- Future datasets should be added as dataset env files plus dataset compose overlays, not as one-off compose copies.
- Shared services (Mailpit, webhook-tester, Keycloak) run as a separate Compose project (`mb_shared`) on a Docker network also named `mb_shared`. Each Metabase stack joins this network via `compose/base.yml` so it can reach shared services by hostname. `make services-up` / `make services-down` manage shared services manually. `scripts/shared-services.sh` does not source `common.sh`; it inlines its own `normalize_docker_path()` (using `cygpath -w` on Windows Git Bash). Commands: `up` (start all), `stop` (stop without removing), `down` (remove), `ensure` (start only active profiles), `ensure-network` (create `mb_shared` network without starting services — called unconditionally from `start.sh` before any stack launches).
- Shared services use Docker Compose profiles so only enabled services start. Each service has a profile: `mailpit` → `email`, `webhook-tester` → `webhooks`, `keycloak` → `saml`. `make services-up` activates all three profiles. `shared-services.sh ensure` reads `ENABLE_EMAIL`/`ENABLE_WEBHOOKS`/`ENABLE_SAML` from the environment and activates only the matching profiles — so starting a stack with only `ENABLE_SAML=true` starts Keycloak but not Mailpit or webhook-tester. `docker compose up -d --profile <x>` is idempotent, so `ensure` always calls it without a pre-check.
- Per-stack optional service flags live in the version env file: `ENABLE_EMAIL=true/false`, `ENABLE_WEBHOOKS=true/false`, `ENABLE_SAML=true/false`. When any is true, `scripts/start.sh` calls `shared-services.sh ensure` automatically. `ENABLE_EMAIL` also includes `compose/email-overlay.yml` so Metabase gets SMTP env vars pointing at the `mailpit` container. `ENABLE_WEBHOOKS` sets `MB_HTTP_CHANNEL_HOST_STRATEGY=allow-private` (required — default `external-only` blocks all Docker network IPs). `ENABLE_SAML` starts Keycloak.

(`MB_ENCRYPTION_SECRET_KEY` in `env/common.env`/`compose/base.yml` is required for OIDC — never rotate it after OIDC secrets have been stored, they're encrypted with this key.)
- **Webhooks**: SSRF host-strategy config, the frontend validation-bug workaround, and session-ID mechanics live in `.github/agent-webhooks.md`; read that only when working on `ENABLE_WEBHOOKS`.
- **Metabot LLM debug logging** (`METABOT_DEBUG_LLM`): file paths and the Linux `chmod` gotcha live in `.github/agent-metabot-debug-logging.md`; read that only when working with this feature.
- **Metabase MCP server**: Metabase itself ships a built-in MCP server exposed as a Streamable-HTTP endpoint at `/api/metabase-mcp` on the same port as the REST API — nothing extra is started to enable it. It's authenticated the same way as the rest of the automation calls in this repo: the `x-api-key` header using `MB_AUTOMATION_API_KEY`. `make start` registers this endpoint as an MCP server in Claude Code (via `claude mcp add -s project`, written to `.mcp.json` which is gitignored) and then immediately runs `claude mcp list` so any pending-approval prompt is surfaced automatically — Claude Code's own built-in MCP client connects directly to it, no separate bridge/proxy process involved. The MCP server name is `COMPOSE_PROJECT_NAME` (e.g. `mb_1_62_3_x_sample_mysql8`), so multiple stacks each get their own named entry. `make nuke` removes the entry. MCP tools are only available in new Claude sessions started after `make start`.
  - **`start.sh` always builds the MCP URL from `127.0.0.1:${METABASE_PORT}`, never from `$MB_SITE_URL`.** These serve different purposes: `MB_SITE_URL` is Metabase's self-referential URL for things browsers/external services need (OIDC/SAML callbacks, email links) and may be deliberately overridden to a hostname that's only meaningful in that context (e.g. a hosts-file entry for SSO testing). The MCP URL is a same-machine, script-initiated API call — the same category as the other loopback calls already in `start.sh` (webhook-channel check/creation, session priming), all hardcoded to `127.0.0.1` for the same reason: it always reaches the port Docker actually published, and sidesteps `localhost` resolving to `::1` first on some systems (a real gotcha since Claude Code's MCP client is Node-based). Do not "fix" this to use `$MB_SITE_URL` — it would make registration fragile exactly when `MB_SITE_URL` is most likely to be non-default.
  - `start.sh`'s summary echo has three `mcp_result` cases: `0` success (prints the MCP URL and an approval reminder), `1` registration ran but failed, `2` no `claude` binary could be found via `resolve_claude_bin` (see below). Cases `1` and `2` both print a ready-to-paste manual command: `claude mcp add --transport http <COMPOSE_PROJECT_NAME> http://127.0.0.1:<PORT>/api/metabase-mcp --header "x-api-key: <MB_AUTOMATION_API_KEY>" -s project`. The `--header` flag is required — omitting it leaves the server in "Needs authentication" state and no tools load.
- **Finding the `claude` binary (`resolve_claude_bin` in `scripts/common.sh`)**: most users only ever run Claude Code through the VSCode/Cursor extension, which never puts a `claude` binary on `PATH` — so a plain `command -v claude` check misses them on every platform (Linux, macOS, Windows/Git Bash), not just one. `start.sh` and `nuke.sh` both call `resolve_claude_bin` instead, which tries, in order: (1) `$CLAUDE_CODE_EXECPATH` (set by the extension for the current session — the fast path when `make start`/`make nuke` run from an integrated terminal), (2) `command -v claude` (standalone npm/brew installs), (3) scanning `~/.vscode{,-server,-insiders,-server-insiders}/extensions` and `~/.cursor{,-server}/extensions` for the newest `anthropic.claude-code-*` folder's bundled `resources/native-binary/claude`(`.exe`). This makes MCP auto-registration work identically on Windows and Kubuntu regardless of whether `claude` was ever installed standalone.
- **Metabase CLI (`mb`) integration**: `scripts/start.sh` also authenticates the official Metabase CLI (npm package `@metabase/cli`, binary `mb`) against the freshly started stack, right after MCP registration. It uses `mb auth login --profile "$COMPOSE_PROJECT_NAME"` — the **same key** MCP registration uses — so concurrent stacks get isolated CLI profiles instead of overwriting each other's credentials under the CLI's `default` profile. The key is passed via the `MB_API_KEY` env var, not `--api-key`, so it never appears in `ps` output. Command resolution mirrors `resolve_claude_bin`'s degrade-gracefully pattern: bare `mb` if on `PATH` (fast — requires `npm install -g @metabase/cli`), else `npx --yes @metabase/cli@latest` (slower, no install needed), else skipped entirely. `cli_result` (0 = success, 1 = login failed, 2 = neither `mb` nor `npx` found) mirrors the existing `mcp_result` pattern and drives an analogous summary block. Like the MCP server, this authenticates as `MB_AUTOMATION_API_KEY` — an **admin-group** key (see `seed/metabase/config-pg15.yml`) — so CLI writes have the same full blast radius as MCP tool calls or raw API calls; treat archives/updates with the same caution.
  - `--profile` is per-subcommand and goes *after* the verb chain (`mb table list --profile x`, not `mb --profile x table list`) — the CLI has no "current profile"/context-switch command, so every invocation from any terminal needs an explicit `--profile`. `mb auth list --json` enumerates all locally saved profiles with a live health probe.
  - The CLI's own bundled docs are the source of truth for its flags and conventions, not the metabase.com CLI docs page or general web search — both have proven unreliable for this specific tool: the docs page names the wrong auth env var (`METABASE_API_KEY` instead of the real `MB_API_KEY`), and a web search summary fabricated a plausible-sounding but impossible detail (a CVE dated *after* the release that supposedly fixed it). Run `mb skills get core` for workflow guidance and confirm any flag against live `--help` output before wiring it into a script — `mb <command> --help` is cheap (~1KB) and covers flags/usage/examples for that one command. Reach for `mb __manifest` only when `--help` can't answer the question, namely a command's **output JSON schema** (e.g. confirming a response actually contains a given key) — it's a ~800KB dump of every command, so pipe it straight into `jq`/Python to filter before it lands anywhere, and fetch it once per session rather than re-running it per command.
  - **`db get`/`db metadata` silently drop nested arrays (like `tables`) in compact mode even when named via `--include`** — `--full` is required for the array to appear at all, not just for extra per-item detail (a real footgun: the command exits 0 with a normal-looking but incomplete response, no warning). Scope `--full` calls to the one table/record actually needed (e.g. `table get <id> --include fields --full`) rather than a whole database's tables+fields — that also avoids the CLI's default 64KB single-response cap, which the bundled sample dataset alone exceeds (~200KB) despite being nowhere near a "real warehouse."
  - Several commands (e.g. `auth logout`) always exit `0` regardless of whether they did anything — check the JSON response body (e.g. `cleared: true/false`) rather than the exit code to know if the operation actually happened.
  - Fresh-machine install: `npm install -g @metabase/cli` — works immediately on Windows (npm's default global prefix is already user-owned). On Linux with a system-package-manager Node, this needs replacing with `nvm` first (apt's default prefix, `/usr/local`, is root-owned — `sudo npm install -g` is not the fix, it just breaks future non-sudo updates). Full playbook — apt removal, verified nvm install, and the non-interactive-shell PATH fix — lives in `.github/agent-linux-node-setup.md`; read that file only when actually bootstrapping or debugging Node on Linux, not for routine work.
  - **`common.sh` exports `MB_CLI_DISABLE_KEYRING=1` unconditionally** — by default the CLI (via `@napi-rs/keyring`) stores the API key in the OS keyring (KWallet/gnome-keyring on Linux, Credential Manager on Windows) instead of its plaintext `profiles.json`. That backend is flaky across reboots/OS/session state: `mb auth login` reports `authenticated: true` while silently failing to persist the key (profile ends up with `"apiKey": null`), so the *next* `mb` call in the same stack fails hard with `{"category":"config","message":"Not authenticated for profile ..."}` — no network attempt, just a config-validation error, and no wrapper error message from `seed-metabase.sh`/`common.sh` since `ensure_mb_cli` itself returned success. This is why a stack can work one boot and fail the next on the same machine, on either OS. Forcing plaintext storage costs nothing here — `MB_AUTOMATION_API_KEY` is a per-stack generated value that only ever lives in gitignored env files, so plaintext local storage adds no exposure beyond what's already true of those files. Don't remove this env var to "fix" a future keyring warning; the warning is expected and intentional.
